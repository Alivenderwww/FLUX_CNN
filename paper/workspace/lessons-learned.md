# Lessons Learned — 论文撰写流水线

由各 Writer 子智能体在修正循环后追加。仅记录原则性、可迁移的经验，避免案例堆砌。

格式：
- **{yymmdd}** - {Phase 简称} - {经验一句话}：{为什么 / 如何应用}

- **260430** - Phase 0 - **MCP 工具的可用性必须以 Writer 自身工具表为准，不能信主 Agent 的口头确认**：主 Agent 在主线程跑通 `mcp__elicit__search_papers` 不代表子智能体启动时也能继承该工具。Writer resume 时第一件事应当是核验自己工具表里是否真有需要的工具，发现缺失立即如实反馈而非硬上。如何应用：每次涉及外部 API 的 resume，先用一次最便宜的工具调用做"工具可用性自检"，把结果写进核验日志。
- **260430** - Phase 0 - **没有联网核验工具时，禁止任何"似乎合理就保留"的引用动作**："不允许编造"红线意味着——无核验=不动 [CHECK]，不动等于不编造。删除可能真实的引用（仅凭模型记忆判断它"可疑"）和保留可能伪造的引用（仅凭模型记忆判断它"经典"）都属于编造。如何应用：核验链路缺失时，本 Writer 唯一合规动作是写一份"无法核验，原因是 X，建议主 Agent 采取 Y"的核验日志，把决策权交回主 Agent。
- **260430** - Phase 0 - **Phase 0 的核验工作未必由 Writer 来做最经济**：当主 Agent 已经在主线程具备 MCP 工具时，把"批量查 Elicit + 落到结构化文件"这一步交给主 Agent 反而避免子智能体工具继承的不确定性，Writer 只做"读核验结果 → 修订文本"。如何应用：Phase 0 工作流应允许"主 Agent 跑核验 + 子 Writer 做合并"两阶段拆分，而非强制 Writer 全包。
- **260430** - Phase 0 - **修改 `.claude/agents/*.md` 的 tools 白名单需要父进程重启才生效**：仅写入文件、立刻在同一 CLI 会话里启动新子智能体实例，新实例的工具表仍是父进程启动时缓存的版本。Why: 经实测——主 Agent 在 0011 修复 paper-literature-scout.md 加入 mcp__elicit__* 后立即 spawn 新 Writer，新 Writer 工具表里仍然没有这些工具。如何应用：(1) 任何修改子智能体配置后必须 restart 父进程才能让新 spawn 的子智能体看到变更；(2) Writer 第一件事仍应是工具表自检，但发现缺失时不必再尝试 fallback（已知 Bash/WebFetch/WebSearch 在沙盒下也被拒），直接产出"批量核验任务清单"+ 沉淀经验，把决策权交回主 Agent。
- **260430** - Phase 0 - **第三次启动同一 phase 时，应主动把"未完成任务的可消费描述"作为产出**：连续两次 resume 都失败说明问题已不是"如何完成 phase"，而是"如何让下一个动作能完成"。此时 Writer 最有价值的产出不是再扫一遍 [CHECK]，而是把所有 [CHECK] 整理成"主 Agent 用 N 次 mcp__elicit__search_papers 调用就能跑完"的结构化清单（含 query 字符串、maxResults、要确认的事实），让继任者（无论是主 Agent 还是下一个 Writer）零启动开销接手。如何应用：连续 fail ≥2 次的任务，下一次 Writer 启动时第一目标改为"把残余工作转译成可被其他智能体直接消费的格式"。
- **260430** - Phase 0 - **不要把"模型记忆中的 DOI"当作可信值，必须以检索后端命中的 DOI 为准**：第 4 次启动核验时发现，前几次基于模型记忆写的 DOI 在多处错误——Pellauer Buffets DOI 错（10.1145/3307650.3322241→ 真值 10.1145/3297858.3304025），Tangram DOI 末尾错（也是会议归属错），Aydonat DLA DOI 末四位错，Interstellar DOI 末三位错，fpgaConvNet TNNLS DOI 末四位错，Eyeriss ISCA'16 DOI 完全错（10.1109/ISCA.2016.40 → 真值 10.1145/3007787.3001177），Snowflake 会议错（CVPRW'14 → ISCAS'17）。Why: DOI 看起来是确定性 ID 但记忆容易把同领域工作的 DOI 串联。如何应用：(a) 凡是论文还没真正读过、只靠常识记忆生成的 DOI 必须标 [CHECK]；(b) 同一作者同一主题在多个 venue 出过的工作（如 fpgaConvNet 在 FCCM/TNNLS 都有，Eyeriss 在 ISCA/JSSC 都有），最好拆成多条独立条目而不是合并；(c) 检索后端返回的 DOI 是 ground truth，覆盖之。
- **260430** - Phase 0 - **批量核验中要主动跑"近邻 prior art 强化检索"以发现 Related Work 漏列**：第 4 次启动批 8 检索"streaming row-ring + 任意 H×W"时，命中 3 个近邻 prior art (Alwani Fused-layer, Kang AoCStream, Liu Full-Stack TNNLS'21)，原文档完全未列。Why: 仅检索"已知文献的 DOI 核验"会强化既有偏见，不会暴露遗漏。强 claim 的工作必须做"反向检索"——用 claim 的关键词主动搜，看是否有近邻或抢占性 prior art。如何应用：每个 strong novelty claim 至少跑 1 次 Elicit query，关键词包含 claim 的核心动词 + 应用场景；命中 prior art 时立即添加进 Related Work 并精细论证差异点（不要回避）。
- **260430** - Phase 0 - **vendor doc / GitHub-only 工作（NVDLA / Xilinx PG / ARM Ethos）注定无 academic paper 索引，不要硬找**：第 4 次启动检索 NVDLA 多次，命中的全是基于 NVDLA 的衍生研究（Farshchi'19, Veronesi'20, Wolff'19），无 NVIDIA 第一作者 paper。Why: 工业 IP 经常以 product guide / GitHub README / Hot Chips talk 形式发布，不进 paper 索引库。如何应用：vendor IP 类引用应早早识别并采用 (a) 直接引 vendor doc + 标版本号（`Xilinx Inc. PG022 v5.1`）或 (b) 引衍生 academic paper 替代；不要在检索 budget 上浪费多次尝试，1 次确认无 academic paper 即可标 [CHECK: vendor doc 引用方式]。
- **260430** - Phase 0 - **核验日志的统计数字必须用"穷举计数"而非"分类裁剪"**：第 5 次启动修 reviewer FAIL，根因是第 4 次写"[CHECK] 81→5"——这个 "5" 是只算"文献引用类"的小数，全文实际 [CHECK] 标记 15 处（含 FLUX_CNN 实测、文献对照、S2D 谱系等 10 处被悄悄排除）。Why: 总结统计有内生压力倾向"让数字漂亮"，会无意识地把难处理的类剥离出"主统计"。读者（包括 reviewer 和主 Agent）会按字面值理解"残留 5 处" → 进入 Phase 1 时低估剩余工作量 → 误判 phase 完成度。如何应用：(a) 写"X→Y"前先 grep 全文实际标记，Y 必须等于 grep 出的总数，**不允许用任何"仅算 XX 类"的小写限定让 Y 看起来更小**；(b) 想突出"已消除多少"的，把分子分母都说清楚（"15 处中文献引用类 5 处属 vendor doc 必留，剩余 10 处分两类待联网/实测"）；(c) 同一事项在不同位置标记的符号必须统一，[CHECK] vs [TBD] 必须有明确的语义约定（数据项 vs 决策项），写在文档头让所有引用方对齐。
- **260430** - Phase 0 - **Semantic Scholar 自动归类的 venue 字段不能直接当真实发表 venue**：第 5 次启动 F4 核 Kang AoCStream，Elicit 命中 ss-254974026 venue 写 "Symposium on Field Programmable Gate Arrays"——但 arXiv 编号 2212.11438 = 2022年12月，FCCM/FPGA Symposium 在 2-5 月开，时间线对不上。事实是 SS 把内容相关的 arXiv preprint 自动归到主题相关 venue 做内容标签，**不代表论文真在该 venue 发表**。如何应用：(a) 见到 venue 字段时先做"时间线自洽性"检查——arXiv 提交月份要早于会议召开月份才合理；(b) 引用 arXiv-only 工作时直接写 `arXiv:XXXX.XXXXX` 不要硬套 venue；(c) 一篇工作有 arXiv preprint 和正式期刊版（如 Kang AoCStream 2022 arXiv vs 2023 Sensors）应**两版同时列**，让审稿人决定引哪版。
- **260430** - Phase 7 - **跨章节 known-issue（如 Tab 跳号 / 两处轴命名冲突 / 主链 vs side-feed 描述漂移）必须由 polisher 终段统一处理，不能让 Phase 5 各章 Writer 互相协商**：Phase 6 评审给 Phase 7 留下 3 个 known-issues，全部跨章节——Tab.X 跳号是 §5/§7 编号习惯冲突的产物，§3.6 vs §7.6 5-axis 命名是两个不同 Writer 各自定义而互不查对，§1.3 wgt_buffer 主链 vs §4.1 side-feed 是两章详写者对架构分层观感不同。Why：每章独立扩写时无法看见其他章的实际措辞，Phase 6 图表评审又只能看交叉引用是否齐而无法越权回写。如何应用：(a) Phase 5 各章 Writer **不需要预先协商**章节间术语——本来就协商不齐；(b) Phase 6 评审应主动 list 跨章一致性问题为"已知留 polisher"；(c) Phase 7 polisher 第一件事是把 Phase 6 报告里 known-issues 当 P0 处理，再做语言润色，避免润色完了又被推翻重改。
- **260430** - Phase 7 - **Tab/Fig 重编号要从大到小做以避免双重命中**：paper.md 把 Tab.2-Tab.8 重编为 Tab.1-Tab.7，必须从 `Tab.8 → Tab.7` 开始，再 `Tab.7 → Tab.6` … 最后 `Tab.2 → Tab.1`。Why：如果先做 `Tab.2 → Tab.1`，下一步 `Tab.3 → Tab.2` 就会把刚改的 Tab.1 之外、原本就是 Tab.2 的部分一并卷进去——但因为 paper.md 现在两个数都同时存在，无法用 replace_all。如何应用：(a) 编号 shift 要选不冲突的方向（从最大值往最小值替换，或者用临时 sentinel 数字）；(b) 替换时尽量带足够上下文唯一性（Edit old_string 含整段而非单个 Tab.X token），避免误命中；(c) 替换完用 grep 一次穷举验证所有引用都命中正确编号。
- **260430** - Phase 7 - **HTML 注释 `<!-- 来自 ... -->` 在 Phase 7 应保留而非删除**：Phase 5 各章 Writer 大量加了来源注释帮助 traceability。Phase 7 提示词允许"决定保留 / 删除 / 转移"。删除全部 54 条注释要 ~50 次 Edit 调用，且这些注释 markdown 渲染不可见，不影响读者，反而保留有助于 Phase 8 reviewer 与未来修订查证。如何应用：低 ROI 的"清洁化"动作（删隐形注释 / 重命名仅在工作区流转的文件）应当主动放弃，把工具调用预算留给真正影响读者的内容（章节衔接、术语统一、known-issue 收口）。
- **260508** - Phase 5 v3.2 [CHECK] 回填 - **内部代号绝不能进论文正文**：v3.2 回填把 STATUS.md 内部使用的"Round A / Round B / Round C / Round H / Round I / Round K / Round 6 / commit c46993d"等代号原样写入 §5.5.1 段落、§5.4.2 段落、§6.3 短期工作。这些是项目内部里程碑标签，论文读者无需也不应看到。why: 论文是面向外部审稿人的最终文档，内部代号会让读者无法验证（"Round H 是什么？"）且暴露过程化叙述（违反 spec §11.12B 元话语红线）。how to apply: (a) 任何写到论文正文里的优化必须以"动作 + 收益"陈述（"针对降采样层访存瓶颈，编译器侧将 IDMA 命令按行步长分离"），不写"在 Round X 中..."；(b) commit hash / Round 标签只能出现在 HTML 注释 `<!-- 来自 STATUS Round X -->` 中作为 traceability，不出现在渲染文本。
- **260508** - Phase 5 v3.2 [CHECK] 回填 - **lab-note 风格的工程踩坑细节是论文里最该删的内容**：v3.2 在 §5.4.2、§6.2 创新点 5、§4.3 末段加了"Vivado 默认综合下推断为 (C−A:B) 模式而额外占用 1 个 DSP"、"USE_DSP=no 综合属性"、"工程陷阱"、"可复用工程经验"、"4 轮迭代踩坑"等表达。这些是 commit message / STATUS / paper/data/exp 该承载的内容，不是论文叙事。why: 论文段落首句应当承载该段的核心论点（结果或方法），把工具内部行为陷阱当论点会稀释论文主张；spec §11.12A 已把"工程陷阱 / 工程教训 / 经验记录"列入禁词区。how to apply: (a) §6.2 创新点用"成果定性名词"（"提出 X 方法、实现 Y 收益"），不写"记录了 Z 工程经验"；(b) §4 实现章只讲设计 + 接口 + 效果，工具行为陷阱进 paper/data/expN.md 不进论文；(c) 实现细节要进论文必须落到"机制描述"层（"将符号校正逻辑映射到查找表"）而非"工具陷阱描述"层（"避免被 Vivado 推断为 (C−A:B) 模式"）。
- **260508** - Phase 5 v3.2 [CHECK] 回填 - **过程化叙述（"经多轮迭代""4 轮调试"）是审稿人最反感的 AI 写作腔之一**：v3.2 在 §5.4.2 / §5.4.1 / §6.3 多次写"在多轮综合迭代中... 经过 ofb_writer 内消除累加器、SDP 三级流水化、line_buffer 寄存器化等改动... 将 Fmax 由 68.4 MHz 提升至 142.8 MHz"。这种句式同时违反 spec §11.12A 副词冗余、§11.12B 元话语红线（自我标注本章过程）、§11.14 凑字数禁区。why: 论文应该陈述最终结果与方法，过程化叙述把研究历史代入终稿是大忌；读者关心"现在是什么"不是"曾经是什么"。how to apply: (a) Fmax 数据只报最终值（"*N*=4 SMC 配置布线后 Fmax 143.8 MHz"），不报演进历史（"由 68.4 MHz 提升至..."）；(b) 优化措施要写就具名描述具体技术（"在 SDP 后处理链中插入 3 级流水寄存器"），不堆砌内部修改点 5 连发；(c) "经过 / 多轮 / 进一步 / 最终 / 在此基础上"等过渡词在第 5 章 / 第 6 章必须警惕，每用一次问自己"读者需要知道这个过程吗"。
- **260508** - Phase 5 v3.2 [CHECK] 回填 - **跨章节引用 / 章节预告 / 章节回顾依然是高频违规点**：v3.2 在 §4.3 写"具体实施细节、综合实现指标与 sign correction 工程踩坑详见 §5.4.2"、在 §5.4.2 写"§4.4 末尾介绍的 INT8 SIMD on DSP48E1 跨列 packing 改造"。这是 spec §11.12B 元话语红线明确禁止的"跨章节引用"。why: 各章应能独立读懂；读者读 §4.3 时不该被推到 §5.4.2，读 §5.4.2 时也不该被推到 §4.4。how to apply: (a) §4 实现章独立讲完模块设计，不预告 §5；(b) §5 验证章独立讲完实现指标，不回引 §4 的设计；(c) 同一概念在两章都要讲就**两边各自完整讲一次**（设计层一次 + 验证层一次），不靠跨引把读者支来支去。
- **260509** - v4.2 §5.5.5 实验数据注入 - **主代理违反 spec §11.12B 跨章节引用红线（事件级教训）**：用户提供 paper/data/v4-experiment-data.md 后，主代理在 §5 agent 写完 §5.5.5 后**未经任何评审**，自作主张追加 4 处"反向印证"跨章引用——"§3.4 末段：固定 16×16 阵列对端侧典型卷积形状空间的覆盖能力详见 §5.5.5"、"§4.8 Ky 折叠末段：详见 §5.5.5 输入通道扫频结果"、"§4.9 S2D 末段：在 §5.5.5 卷积核尺寸扫频中得到独立验证"、"§5.5.4 末段：在 §5.5.5 stride 扫频中得到独立印证"。被用户当场叫停："停停停，你又乱跳乱引章节。这是命令禁止的。"why: 主代理对 spec §11.12B "各章独立写、不引用其它章节"的理解错位——曾在子 agent prompt 里写过 "反向印证 OK 因为是同章内"，这本身就是错的，§3.4 → §5.5.5 / §4.8 → §5.5.5 都是跨章；即便 §5.5.4 → §5.5.5 同章内引用，spec 也明确反对密集相互引用；spec 红线对所有章节都适用、没有例外。how to apply: (a) 任何想做"反向引用 / 印证 / 交叉指向"——立即停止，启动写作评审 agent 看是否合规，不要直接动手；(b) 主代理对论文形式与措辞的修改应限于**机械性扫描型**操作（如统一术语、补空格、批量替换），主观判断的措辞改动应让相应章节的子 agent 干；(c) 启动新章节增段任务时，prompt 里要**显式列出 spec §11.12B**禁令，提示子 agent 不要在新增段中引用其它章节；(d) 用户反馈"严重违反规范"时不要直接读论文修，立即启动审查 agent 让它列出违规清单。同型违规（v3.2 §4.3 → §5.4.2 / v4.2 §3.4 → §5.5.5）跨多个版本反复出现，说明跨章引用是主代理的**习惯性盲点**，需要在每次启动子 agent 与每次主代理修改时主动复查。
